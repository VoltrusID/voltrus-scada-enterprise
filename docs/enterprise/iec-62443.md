# IEC 62443 security audit mode

What it is: a security event log with filters, CSV export, detection thresholds
and a retention hold, to give an IEC 62443 assessment (SR 2.8 auditable events,
SR 2.9 audit storage, SR 6.1 audit log accessibility) evidence from the SCADA
server. It is **not** an IEC 62443 certification of the product or of your
system, and it does not configure your network zones and conduits. Licence:
Enterprise (`iec_62443` on `GET /api/license/status`). Code:
`enterprise/src/audit/handlers.rs`; the events are written by the core
(`core/src/security/intrusion.rs`, `core/src/api/auth/handlers.rs`,
`core/src/cache.rs`).

## What is recorded

The core records these events on every install; the Enterprise licence makes
them viewable, exportable and kept.

| `event_type` | Severity | When |
| --- | --- | --- |
| `login_failed` | warning | Wrong password or unknown user at sign-in |
| `login_locked` | warning | Sign-in attempt on a locked account (10 wrong passwords lock it for 15 minutes) |
| `login_disabled` | warning | Sign-in attempt on a disabled account |
| `auth_401` | warning | More than `suspicious_401_threshold` unauthorised requests from one IP within `suspicious_401_window_secs` |
| `config_change` | info | Security thresholds changed |
| `device_connected`, `device_disconnected` | info, warning | A polled device comes online or drops |
| `signature_auth_failed` | warning | Wrong password at a 21 CFR Part 11 signature ([part-11.md](part-11.md)) |

Each event has time, source IP and user agent when known, user name and a
detail text. User and configuration actions (who changed what) are in the
separate, hash-chained audit log (**More actions (⋯) › Audit Log**,
`GET /api/v1/audit`, chain check `GET /api/v1/audit/verify`).

## Set up

1. Check the licence: **More actions (⋯) › Data Manager › Admin › License**
   shows Enterprise.
2. Open **Data Manager › Admin › Security** (admins only). The list shows the
   newest events first; filter by event type, severity and time.
3. Expand **Threshold Configuration** to tune detection, then **Save**:
   * `suspicious_401_threshold` / `suspicious_401_window_secs`: used, they
     drive the `auth_401` event.
   * `failed_login_threshold`, `failed_login_window_secs`, `rate_limit_threshold`,
     `rate_limit_window_secs`: stored and exported with the project, **not used
     yet**. Sign-in lockout is fixed at 10 wrong passwords for 15 minutes and
     the request rate limit uses the core defaults.
   The same values are `GET`/`PUT /api/v1/security/thresholds`.
4. Retention: nothing to do. With the licence, the security log and the audit
   log are kept regardless of `retention.security_keep_secs` (the server logs
   `retention.security_keep_secs is ignored: the licence includes IEC 62443
   mode` at start). Export them before you prune the database by hand.

## Export

**Data Manager › Admin › Security › Export CSV**, or
`GET /api/v1/security/events/export?from=<unix>&to=<unix>` (admin). The file
is `security-log-<date>.csv`. The list API is
`GET /api/v1/security/events?event_type=&severity=&from=&to=&limit=&offset=`
(at most 1000 per page).

## Check it works

1. Sign in once with a wrong password. **Security** shows `login_failed` with
   your IP and the user name.
2. Export CSV and open it: the same row is there.
3. `GET /api/v1/security/events?event_type=login_failed` returns it.

Verified on 2026-11-16 with a stub-licence build: `signature_auth_failed`,
`device_connected` and threshold changes were listed and exported.

## Troubleshooting

| Symptom | Fix |
| --- | --- |
| `403 Security audit requires an Enterprise licence` | Integrator or no licence; check **Admin › License**. |
| The **Security** tab is missing | You are not signed in as an admin (operators do not see it). |
| No `auth_401` events although scanners hit the server | The threshold is per IP and window; lower `suspicious_401_threshold`, or the requests come through a proxy that hides the client IP. |
